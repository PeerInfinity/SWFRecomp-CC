# SWFRecomp-CC

SWFRecomp-CC is a **static recompiler for Flash**. It translates the bytecode in a SWF file (AVM1 / ActionScript 1–2
and AVM2 / ActionScript 3) into C ahead of time. The generated C is compiled together with a runtime library, either
into a native executable or with Emscripten into WebAssembly that runs in the browser on WebGPU. There is no
interpreter at run time: each ActionScript method becomes a C function.

The idea comes from [N64Recomp](https://github.com/N64Recomp/N64Recomp) by Wiseguy, by way of LittleCube's
[SWFRecomp](https://github.com/SWFRecomp/SWFRecomp), which this project forked in October 2025 (see
[Relationships](#relationships) below).

**New here?** [`GETTING_STARTED.md`](GETTING_STARTED.md) builds the recompiler and runtime and runs one Ruffle test,
in about five minutes on a stock Ubuntu 24.04 machine.

## The goal: match Flash Player 32

The target is the behaviour of **Adobe Flash Player 32**, the last release, for both trace output and rendered pixels.

- **The instrument is Ruffle's test corpus.** [Ruffle](https://github.com/ruffle-rs/ruffle)'s `tests/tests/swfs/`
  tree (its own tests plus the ones it imported from Gnash, Shumway and Adobe's Tamarin/avmplus) is mirrored by
  `ruffle-tests/download_tests.sh` and run on every CI run. It is the broadest public description of Flash behaviour.
- **The oracle is a real Flash Player 32.** The debug projectors (Linux and Windows) are scripted locally by
  [`tools/flash-oracle/`](tools/flash-oracle/README.md). Where a Ruffle golden disagrees with what FP32 actually does,
  the FP32 capture wins: the corrected golden is stored in [`ruffle-tests/flash_fixes/`](ruffle-tests/flash_fixes/README.md)
  and re-applied after every download, and the difference is written up in
  [`RUFFLE_VS_FLASH_DIFFERENCES.md`](ruffle-tests/tests/swfs/avm1/_investigation/RUFFLE_VS_FLASH_DIFFERENCES.md).
  The Flash binaries themselves are never committed or uploaded anywhere.
- **The second purpose is speed in the browser.** Recompiled AVM2 games run without interpreter dispatch, which is
  what makes games such as Seedling playable in a browser tab (see [Live demos](#live-demos)).

## Code map

| Path | What is there |
|---|---|
| [`SWFRecomp/`](SWFRecomp/README.md) | **The recompiler** (C++). `src/swf.cpp` and `src/tag.cpp` parse the SWF; `src/action/action.cpp` translates AVM1 bytecode to C; `src/abc/` parses, verifies and emits AVM2 (ABC) code; shapes and glyphs are tessellated at recompile time. `scripts/` builds native and WASM targets. |
| [`SWFModernRuntime/`](SWFModernRuntime/README.md) | **The runtime** (C) the generated code links against. `src/actionmodern/` is the AVM1 VM (`action.c` is the core); `src/avm2/` is the AVM2 VM and the flash.* class library; `src/libswf/` is the player loop, display list and tags (`swf.c` with rendering, `swf_core.c` headless); `src/rendering/render_webgpu.c` is the WebGPU renderer (native through Dawn, browser through Emscripten); `src/audio/`. |
| [`ruffle-tests/`](ruffle-tests/README.md) | **The test harness.** `verify_output.py` recompiles, compiles and runs one test and compares it with its golden. `download_tests.sh` fetches the upstream corpus (not stored here). `tests/swfs/regression/` is this project's own fixture suite (tracked). `results/` has the cross-suite tables. |
| [`SWFRecompDocs/`](SWFRecompDocs/README.md) | Docs: [`ARCHITECTURE.md`](SWFRecompDocs/ARCHITECTURE.md) (how it works, and how it differs from Ruffle), `plans/PROJECT_STATE.md` (current state), guides, specs, reference notes. |
| `tools/` | Flash oracle, divergence harnesses (where our run first differs from Ruffle or Flash), browser drivers, SWF analysis, perf rigs. |
| `scripts/` | CI result processing, environment setup, the Dawn build. |
| `docs/` | The GitHub Pages site above (`docs/recompiler/` is the in-browser recompiler). |
| `demos/` | ActionScript sources for some of the demo pages. |
| `docs2/` | A local-only demo site for SWFs that are **not** freely licensed. It is never deployed, and the game files are not tracked. |
| `.github/workflows/` | CI. `ruffle-tests.yml` runs the corpus (manual dispatch, sharded); `deploy-pages.yml` builds and deploys the site. |

The pipeline in one line: `test.swf` → `SWFRecomp` → `RecompiledScripts/*.c` + `RecompiledTags/*.c` (+
`RecompiledABC/` for AVM2) → `gcc` or `emcc` with `SWFModernRuntime/` → a native binary or a `.wasm` page.
The full walk-through, written for Ruffle developers, is
[`SWFRecompDocs/ARCHITECTURE.md`](SWFRecompDocs/ARCHITECTURE.md).

## Relationships

### Ruffle

[Ruffle](https://ruffle.rs/) is the Flash emulator that actually preserves Flash content today, and this project
leans on it heavily. Its test suite, and the work behind it (including what it imported from Gnash, Shumway and
Tamarin), is how we measure ourselves, and Ruffle's source is our first reference for how a Flash API behaves. The
architecture is different (ahead-of-time C emission plus a C runtime, where Ruffle is an interpreter in Rust;
[ARCHITECTURE §5](SWFRecompDocs/ARCHITECTURE.md#5-main-differences-from-ruffles-design) compares them), but
many behaviours were ported from Ruffle's Rust to C: number formatting, array sorting, ByteArray, BitmapData, timers
and more: 165 functions, tables and shaders in 63 files. Each one names its Ruffle source file in a comment, and they
are all listed in [`SWFModernRuntime/third_party/ruffle/README.md`](SWFModernRuntime/third_party/ruffle/README.md).
That code is used under Ruffle's MIT licence ([`LICENSE-MIT.txt`](SWFModernRuntime/third_party/ruffle/LICENSE-MIT.txt),
listed in [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md)).

Where our results and Ruffle's disagree, we check against real Flash Player 32. When FP32 shows that one of Ruffle's
goldens is wrong, that is recorded in
[`RUFFLE_VS_FLASH_DIFFERENCES.md`](ruffle-tests/tests/swfs/avm1/_investigation/RUFFLE_VS_FLASH_DIFFERENCES.md) with the
evidence, and the corrected golden lives in [`ruffle-tests/flash_fixes/`](ruffle-tests/flash_fixes/README.md). Both are
public, for anyone who wants to check them, Ruffle's developers included.

### Upstream SWFRecomp

SWFRecomp-CC forked from LittleCube's [SWFRecomp](https://github.com/SWFRecomp/SWFRecomp) and
[SWFModernRuntime](https://github.com/SWFRecomp/SWFModernRuntime) in October 2025. Since July 2026 the two are a
**permanent friendly fork**: they share the idea and exchange knowledge, but not code, because the architectures have
diverged too far to merge either way. Upstream is the architecture project (thread-safe context, concurrent GC,
string-ID properties, an AS2 prelude standard library, SDL3). This repository is the behavioural-parity project (the
full test corpus, AVM1 and AVM2, native and browser builds, playable games). Decision record:
[`SWFRecompDocs/merge/upstream-relationship-2026-07.md`](SWFRecompDocs/merge/upstream-relationship-2026-07.md); what each
side does better: [`SWFRecompDocs/upstream-comparison/`](SWFRecompDocs/upstream-comparison/). Behavioural findings
about upstream's code are reported as issues there.

The older forks [PeerInfinity/SWFRecomp](https://github.com/PeerInfinity/SWFRecomp) and
[PeerInfinity/SWFModernRuntime](https://github.com/PeerInfinity/SWFModernRuntime) carried the 2025 work before the
repositories were combined here; they are not used any more.

## How this project is developed

SWFRecomp-CC is developed with [Claude Code](https://claude.com/claude-code) sessions, directed by the maintainer.
That is why the root has a [`CLAUDE.md`](CLAUDE.md) and a `.claude/` directory: `CLAUDE.md` is the agent manual
(workflow rules, test commands, architecture traps), and it is also a fair summary of how to work in this tree. The
session-by-session record (fan-out reports, session briefs, dated status logs) lives in a separate public repository,
[SWFRecomp-CC-history](https://github.com/PeerInfinity/SWFRecomp-CC-history), at the same relative paths; citations in
this repo written as `SWFRecomp-CC-history:<path>` point there.
