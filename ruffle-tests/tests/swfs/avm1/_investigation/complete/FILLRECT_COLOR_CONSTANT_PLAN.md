## Status: NOT STARTED

### Problem

The `bitmap_data_fillrect` headless image test has 218 wrong pixels (545 channel outliers) at x=[147,209], y=[20,29]. These pixels show red (255,0,0,255) instead of expected blue (0,0,187,255).

**Current image result:** 545 outliers, max diff 255

### Root Cause

The recompiler (`SWFRecomp`) generates the wrong double constant in the C code. In the `testFillTransparent` function at `script_defs.c:391`:

```c
PUSH(ACTION_STACK_VALUE_F64, 0x41E55FE000000000ULL);  // WRONG: decodes to 0xAAFF0000 (red)
```

The correct value should encode to `0x440000BB` (blue with alpha=0x44), matching the bitmap's initialization color. The test expects a blue transparent bitmap filled with a blue color, but gets red instead.

**Value analysis:**
| | Hex bits | Double | ARGB | Color |
|---|---|---|---|---|
| Current (wrong) | `0x41E55FE000000000` | 2868838400.0 | `0xAAFF0000` | Red, A=170 |
| Expected (correct) | `0x41D100002EC00000` | 1140850875.0 | `0x440000BB` | Blue, A=68 |

### This is a Recompiler Bug

The issue is in `SWFRecomp/src/action/action.cpp`, in the code that reads `ActionPush` double constants from SWF bytecode and emits them as C hex literals. The SWF bytecode stores doubles in a specific byte order, and the recompiler must correctly encode them as `0x...ULL` hex literals for the generated C code.

### Investigation Needed

1. **Check the SWF bytecode directly** — verify what double value is actually in the `test.swf` file at the corresponding bytecode offset. Use a hex editor or SWF parser to read the Push(double) instruction.

2. **Check the recompiler's double encoding** — in `action.cpp`, find where `ActionPush` type 6 (double) is handled. The SWF spec says doubles are stored as 8 bytes in a specific order (the two 32-bit halves may be swapped relative to IEEE 754).

3. **SWF double byte order** — Per the SWF specification (swf-spec-19.txt), Push(double) stores the double as two 32-bit words with the LEAST significant 32 bits first, then the MOST significant 32 bits. This is NOT standard little-endian byte order for doubles. The recompiler needs to swap the two 32-bit halves when reading.

4. **Verify the swap logic** — The recompiler likely has a byte-swap when reading doubles. If this swap is incorrect or inconsistent, some values would be decoded wrong while others work fine (most doubles with simple values like 0.0, 1.0, etc. are symmetric or zero in one half and work regardless).
